ShopVerse — Project Report

1. Problem Statement

An online marketplace must serve three different kinds of user simultaneously — customers who browse and buy, sellers who list products and fulfil orders, and administrators who oversee the platform. Each role needs a different view of the same underlying data, and none may read or modify what belongs to another.

Systems of this kind fail in predictable ways. Stock oversells when two customers order the last unit at the same moment. Any authenticated user can call any route because role checks were never added. Order status becomes an editable text field, so invalid jumps such as Delivered back to Shipped pass unnoticed. Coupons are validated in the browser and trusted by the server. A later price change silently rewrites the totals of orders already placed. A single unhandled promise rejection takes the whole server down.

ShopVerse addresses these directly: it is a REST API and web frontend in which the rules that make an e-commerce system correct — not merely functional — are enforced on the server and verified by an automated test suite.

2. Objectives

  1. Build a secure REST API using JWT authentication and bcrypt password hashing.
  2. Enforce role-based access control across Customer, Seller and Administrator roles.
  3. Model the catalog, cart, orders, coupons and reviews in MongoDB with deliberate, documented embed-versus-reference decisions.
  4. Implement the full order lifecycle as a controlled state machine rather than unrestricted database updates.
  5. Keep inventory correct under concurrent access.
  6. Validate every incoming request server-side and return consistent, documented JSON errors.
  7. Provide seller analytics and administrative reporting using MongoDB aggregation pipelines.
  8. Demonstrate the whole system through a Postman collection and a working web frontend.

4. System Architecture

The application follows an MVC-style layering. A request passes downward through the stack, and any failure at any level is converted by a single error handler into a consistent JSON response.

5.1 Why order items are embedded snapshots

This is the most consequential modelling decision in the project. Order items are embedded and they copy the product's name, image and price at the moment of checkout, rather than referencing the live product for display.

An order is a historical record. If it referenced the product and the seller later raised the price or renamed the item, every past order would appear to change retrospectively — the customer's invoice would no longer match what they paid. Because the item is snapshotted, the order remains a faithful record even if the product is later edited or deactivated. The product ObjectId is still stored alongside the snapshot, so the catalog can be reached when it is genuinely needed.

7. Security Implementation

ControlImplementation
Password hashingbcrypt at cost factor 10, applied in a pre('save') hook guarded by isModified('password') so a profile update never double-hashes.
Password exposureThe field is declared select: false; it is only ever loaded explicitly during login.
AuthenticationSigned JWT access tokens. The user is re-read from the database on every request, so deactivating an account revokes access immediately.
AuthorizationRole gates and ownership checks on every write route, producing 403 distinctly from 401.
Account enumerationLogin returns one generic message for both a wrong email and a wrong password.
Input validationexpress-validator chains on every write route, with Mongoose schema validation beneath as a second layer.
Injection safetyAll queries go through Mongoose with typed schemas; :id parameters are ObjectId-validated before reaching the database.
Secrets managementConnection string and signing keys live only in .env, which is git-ignored; .env.example documents the keys with empty values.
Transport hardeninghelmet security headers and a strict CORS origin allowlist.
Brute forceRate limiting applied to authentication routes per IP.
Error leakageStack traces are logged server-side and never returned in production responses.

14. Known Limitations

The following are out of scope by design, consistent with the boundaries stated in the project brief.

  • The payment gateway is mocked; no real transaction is processed.
  • No email or SMS notification service is integrated.
  • A single currency (INR) and a single time zone are assumed.
  • Product images are external URLs rather than uploaded files.
  • Social login is not implemented; authentication is a self-built JWT flow.
  • Multi-document transactions are not used; stock safety is achieved instead through atomic conditional updates, which is sufficient for the single-document guarantees required here.

15. Conclusion

ShopVerse implements the complete product-to-order lifecycle for three distinct roles on a MongoDB schema whose embed-versus-reference decisions were made deliberately and documented rather than chosen arbitrarily.

What separates it from a CRUD application is that the rules are enforced where they cannot be bypassed. Inventory is correct under concurrency because the stock guard sits inside the update query. The order lifecycle is a declared state machine rather than an editable field. Authorization is checked per role and per record, returning 401 and 403 as distinct outcomes. Coupons and reviews are re-validated on the server and never trusted from the client. Every error, from a malformed ObjectId to a violated unique index, is translated into a consistent JSON response with a stable machine-readable code.

The result is verified rather than asserted: 326 assertions across 104 requests pass against a live Atlas cluster, and no tested path returns a 500.
